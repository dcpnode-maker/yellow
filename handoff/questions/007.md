## Decision B — migration tracking model (Tier 3)

The BUILD-PLAN allows Drizzle or raw SQL; `DECISIONS.log` requires Bun-native tooling. Proposed direction: a raw-SQL runner using `Bun.sql`, lexically ordered numbered files, one transaction per migration, checksum validation, and an advisory lock.

Architect decisions required:

1. May the runner create a new `schema_migration` tracking table? A new table is otherwise forbidden without approval.
2. If yes, specify its exact columns, ownership, privileges, and whether it is platform metadata exempt from tenant RLS.
3. Is one transaction per file correct, or must the full pending set be atomic?
4. What advisory-lock key and checksum algorithm are canonical?
5. Must checksum mismatch hard-fail even for the immutable baseline?
6. Confirm that `migrations/0001_init.sql` remains byte-for-byte untouched.

Required proof proposed for the eventual order:

- Fresh database applies `0001` exactly once.
- Second run is a no-op.
- Concurrent runners serialize and apply once.
- Changed checksum hard-fails.
- Failed migration rolls back its transaction and is not recorded.

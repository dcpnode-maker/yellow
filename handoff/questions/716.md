# Question716 — cashier approval readback boundary

The existing `GET /api/v1/properties/:property/cashier-sessions` returns configured drawers, active session, latest count/count history and permission flags. It does **not** return pending or decided approval-request status. The existing approval request and approve/reject POSTs return exact server-owned receipts, while the relevant fresh drawer GET can only confirm that the receipt's session and count remain current.

Order716 will not add a new approval query, route, table or permission. For approval actions the UI can confirm an exact canonical response/replay receipt and matching fresh session/latest count, then display the receipt's approval ID/status as operation evidence; it cannot independently claim that a later GET re-observed approval state. Unknown outcomes retain the exact request and idempotency key and remain locked until same-key replay yields that receipt. A supervisor must receive and enter the approval UUID through the existing operational handoff; the backend, not UI, enforces distinct-user four-eyes authority.

This is a bounded read-contract limitation, not permission to infer an approved discrepancy from amounts or to show expected cash during blind count.

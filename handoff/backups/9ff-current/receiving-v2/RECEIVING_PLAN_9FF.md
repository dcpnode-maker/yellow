# Receiving plan for pinned 9ff source

This is a source receiving plan for base `e06e400a` and cloud `9ff27ad8765dc75ebae9e083d4635c7a9b89fa62` (tree `4311a79c0c9ffc33877809162b1b38ae1b3c944a`). The source manifest records only committed base-to-cloud hunks and exact blob identities for four protected paths. The laptop reports 28 overlapping and 89 shared paths; those counts are controller-reported and are not reconstructed here. No laptop commit, tree, file identity, hunk, applied ledger, or selected source subset was supplied. A missing laptop inventory record must remain **unobserved**, never be treated as laptop absence.

The receiving classifier consumes only an explicitly supplied JSON metadata inventory. It reads no repository, source, credential, environment, database, or image files. Each observed file identity carries its Git blob ID, SHA-256, and exact Git file mode (`100644` or `100755`); unknown mode is null and observed absence has null blob, digest, and mode. `PROTECTED_APP_API_HUNKS.json` also records the Git mode for every base/cloud hunk path. Symlink (`120000`) and submodule (`160000`) entries are explicitly unsupported. Its `cloud_only_guarded_apply` result and `may_apply` flag are metadata-only candidates: they never apply source and require revalidation of actual receiving bytes and mode plus reviewer approval. Diverged paths require manual hunk review, and unknown identities cannot authorize application. Missing laptop records mean unobserved; an explicit null laptop record is invalid. Windows case-colliding paths are rejected. Additions and deletions are represented as observed null identities, distinct from missing observations.

## Protected source contract to preserve

- **CRS route and tenant wrapper:** retain `POST /api/v1/crs/availability:search` under the existing `options.operatorApi` application route, with `withOperatorTenant(request, ...)` and `{ parse: "none" }`. Keep raw stream handling in `readCrsSearchJson`; do not let framework JSON parsing pre-consume or reinterpret the body. The operator handler must keep the current transaction-local tenant context and `inventory.availability:read` scope.
- **CRS authorization and evidence:** validate and snapshot every canonical search, then establish the authenticated actor's current exact-property or ancestor grant for every requested property before calling the offer service for any property. Unknown, foreign, or ungranted properties fail the whole request generically. Search serially in the existing tenant transaction and return the unchanged full canonical offer serializer/evidence, in request order, with no partial success. No lowest-rate, currency aggregation, booking, payment, or inventory write is implied.
- **Departure queue role filtering:** parse only one canonical `target_role_id` on the property queue. Reservation history and command routes reject query strings. Perform normal read scope/property checks before querying. The domain query filters confirmed requests by the exact target role ID in its existing tenant/property-scoped request read, before the bounded 100-row cap; it does not separately resolve the requested role against active role authority. Unknown or foreign role identifiers yield no matching request rows after the same property read authorization; the filter grants no task or command authority.
- **Departure property-mode ordering:** preserve the domain queue priority: confirmed requests with task status `open`, `assigned`, or `in_progress` first, then other confirmed requests, with each group ordered by `due_at,id`. Preserve all current task state, proposal, role-membership, version, idempotency, and audit rules. Do not turn role filtering into a new domain permission.
- **Physical offer siblings:** retain every published physical sellable/rate pair through candidate counting and the existing exact immutable quote loop, including blocked, unpriced, and conflict evidence. Do not deduplicate by unit type or let raw sort order select a representative sibling. Keep current filters, exact quote/policy/tax/publication evidence, currency/minor-unit representation, deterministic ordering, pre-quote work ceiling, and hold/commit arbitration. This is a separate but overlapping change in `offers.ts`; preserve it alongside CRS.

Request those exact laptop-owned migration sources and their strict schema contracts as a separate metadata/source-bound review. Require before/after schema fingerprints and exact applied-ledger evidence; source presence and `CURRENT_MIGRATION_FRONTIER` metadata do not establish application.

For the integrated release, verify applied-ledger checksums and schema, execute `assertRuntimeReleaseReadiness`, and retain historical-prefix fixtures. Keep current source frontier, historical frontier claims, image/source revision, and each database's applied migration ledger as separately identified evidence. Historical proofs tied to 100 cannot certify later source or a database with migrations 101–103.
- **No whole-file substitution.** Review base, cloud, and laptop identities path by path; preserve laptop-only source and shared identical blobs, and manually resolve divergent hunks, including additions/deletions. Do not overwrite protected App/API files wholesale to receive this source slice.

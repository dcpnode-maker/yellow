# Yellow four-day Spark + free/local work schedule

This schedule is the authoritative acceleration queue for the next four working
days. It does not redefine Yellow's completion target. The public demo remains the
source of truth; every implementation begins from a scoped order and ends in
executable browser/domain proof.

## Lane contract

| Lane | Purpose | May edit? | Cost/availability truth |
| --- | --- | --- | --- |
| Codex coordinator | Architecture, integration, hard blockers, final release | Yes, one writer | Uses Codex allowance only when explicitly active |
| Codex Spark | Routine implementation/tests in an isolated candidate | Only inside exact order scope | Prepared here; founder must select/launch Spark in a supported Codex UI |
| Goose + OmniRoute free | Research, order/test proposals, bounded low-risk implementation only after an order grants it | Proposal-only under Order608 | Explicit `:free`; subject to provider quota/availability |
| Laptop Qwen 9B | Deeper bounded audit/proposal | Proposal-only | Fully local; do not load while Docker review runtime is live |
| OnePlus 10R/11R Qwen 4B | Tiny classification/test matrices/second opinions | Proposal-only | Fully local; only while authenticated, cool and healthy |
| Independent reviewer | Personally executes risk-appropriate proof | Review files only | Must not be the implementer |

One writer lease exists across all lanes. A packet cannot move from `prepared` to
`accepted` without its named evidence. “Sent,” “running,” and “model replied” are not
completion states.

## Day 1 — release closure and exact next-order design

Goal: freeze the shareable baseline, then convert remaining founder journeys into
small executable orders without rediscovering completed PMS03/PMS04 work.

1. **D1-01 Order605 public closure** — independent reviewer executes public health,
   asset equality, guarded 240/375/1440 browser checks and read-only 130-table
   postflight. Output: accepted review/ledger or exact blocker. No model substitutes.
2. **D1-02 PMS05 executable gap map** — Goose/Omni-free reads only the capability
   ledger and exact accepted reservation contracts/tests. Output: action-by-action
   table for create, edit, cancel, reinstate and no-show: canonical service/route,
   existing UI/Overwatch coverage, missing tests, risk and smallest order boundary.
3. **D1-03 PMS05 hostility matrix** — 11R microtask proposes cases for duplicate key,
   stale reservation, inventory conflict, changed rate/policy, illegal state,
   ambiguous guest and uncertain response. Output is test cases only.
4. **D1-04 PMS05 source/test locator** — 10R microtask maps named files/symbols from a
   coordinator-provided excerpt; it must return `unknown` rather than invent paths.
5. **D1-05 Order drafting** — coordinator converts verified D1-02..04 evidence into
   separate orders for reservation create/edit and cancel/reinstate/no-show. Tier and
   independent-review requirements are explicit before code begins.
6. **D1-06 Spark packet preparation** — create two bounded Spark prompts with exact
   order, candidate source, allowed files, forbidden actions and tests. Status remains
   `prepared-unlaunched` until a Spark-capable task is actually started.

Exit: Order605 accepted or blocked with evidence; two PMS05 implementation orders
exist; no public write; every worker output has a receipt and source hash.

## Day 4 — confirmation-gated operations, cumulative proof and release

Goal: integrate only accepted work, prove the configured synthetic hotel journeys,
and publish one traceable candidate.

1. **D4-01 AI01 parity audit** — compare the delivered manual actions with Yellow/
   Overwatch typed catalogue. Every supported mutation must have missing-field
   questioning, explicit proposal, separate confirmation, stable retry and
   authoritative refresh. Unsupported actions remain disabled and truthful.
2. **D4-02 multilingual/voice proof** — verify Indian-English default, silent output
   until explicit Speak consent, text fallback, interruption state and at least the
   already supported multilingual navigation paths. Do not claim native Gemini Live
   audio unless the actual transport executes.
3. **D4-03 synthetic property journey pack** — run named arrival, in-house, cashier,
   bill-window, departure/service and completed-history scenarios against the exact
   synthetic property. Destructive/financial writes use disposable proof data unless
   a release order separately authorizes a public action.
4. **D4-04 standing gates** — focused tests, strict TypeScript, boundaries, full suite,
   licence/audit/schema checks and exact PostgreSQL referee 11/11.
5. **D4-05 independent review** — non-implementer personally runs high-risk proofs
   and checks source/container/asset identity, rollback evidence and table
   fingerprints.
6. **D4-06 public release** — only an accepted release order may rebuild/recreate the
   app and start/retain the tunnel. Guarded 240/375/1440 public browser proof and
   postflight fingerprint must pass before notifying the founder.

Exit: one verified public candidate and an updated capability ledger stating exactly
what is complete, partial, blocked or unstarted. Four days never converts partial
evidence into a whole-PMS claim.

## Spark-ready prompt template

Each Spark task receives this exact structure:

```text
Role: bounded implementation worker; no delegation.
Objective: <one order objective>.
Scope: <exact candidate and order>.
Allowed files: <closed list>.
Forbidden: scope expansion, dependencies, migrations/DB/runtime/credentials unless
the order explicitly names them; no commit/merge/deploy; never overwrite unrelated
dirty work.
Evidence required: exact diff, file/symbol locations, before/after behavior.
Validation required: named focused commands and outcomes.
Return: conclusion, evidence, files_and_lines, tests_or_checks, risks,
recommended_parent_action.
```

## Host-control policy

Models do not open or close the hosted app directly. They emit a typed capability
request. The controller may execute only `status`, `review-start` or `review-stop`
through `tools/local-ai/yellow-host.ps1`, then records exact container IDs and health.
It never deletes containers/volumes, runs a seed, rotates credentials or performs a
database action. The currently shareable public demo is not stopped for ordinary
proposal work.

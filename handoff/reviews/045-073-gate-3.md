## F11 — five inherited Tier-3 proofs fail at the tip on a false-positive SQL guard

**Severity: moderate** · Orders 048, 050, 051, 052, 057 · `src/http/operator/operator.js:1354`

Five operator suites assert the browser bundle contains no SQL:

```js
expect(js).not.toMatch(/\b(?:SELECT|INSERT|UPDATE|DELETE)\s/i);
```

All five now fail. The **only** matching text in `operator.js` is UI copy:

```js
1354:  if (!builderReleaseId) return setBuilderMessage("Save or select a draft before previewing.", true);
```

The English words "select a" match the case-insensitive guard. I bisected the asset: the
match first appears in `259d5ec` (guided expert rate workbench) and persists at `3fb6b5b`.

**There is no SQL in the browser bundle. The security property the guard exists to protect
is intact.** But five pre-registered proofs are red at the tip, and under D-92 that is a
hard floor. It went unnoticed because of a structural gap worth naming in its own right:
**five orders' proofs assert against one shared mutable asset, and nothing re-runs them
when that asset changes.** These suites are also database-gated, so they skip in CI's
`bun test` (49 pass / 238 skip) — they only run when a human sets the env by hand.

**What to do.** Do not delete the assertion and do not quietly reword the UI string to dodge
it. Narrow the guard so it tests the actual property — SQL *syntax*, not English words —
for example requiring a verb paired with a clause keyword (`FROM`, `INTO`, `SET`, `WHERE`,
`VALUES`) within a short window. Do it in a bounded order with the reasoning recorded,
because narrowing a guard is weakening unless the false positive is demonstrated, and here
it is demonstrated. Then re-run all five suites.

**What to do.** Derive the figure from `handoff/reviews/` the way `state.sh` derives phase

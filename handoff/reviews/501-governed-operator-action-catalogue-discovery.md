## Decision

Reuse canonical operator APIs. Do not let an LLM invent HTTP requests, execute arbitrary SQL, bypass readiness, or declare a navigation link to be an action. Start with a typed read catalogue and inline results; add explicit per-command adapters in separately reviewed slices. Every write needs authoritative preflight, a proposal, permission checks, one durable idempotency identity, execution feedback, and re-read of the authoritative result. Money and occupancy remain entirely server-authoritative.

The first implementable slice needs no new domain contract: render reservation board/detail, selected guest's reservation history, check-in readiness/candidates and selected folio statement inside Overwatch. Add selection/context state and loading/failure/stale states. This fixes the link-handoff behavior without pretending the missing command surfaces exist.

## Catalogue contract

Each entry should declare `capabilityId`, journey IDs, read/write/admin/external risk, route+method, typed input/output, permission scopes, selection identity, authoritative preflight, confirmation policy, idempotency placement, stale token/expected-state policy, domain service, effect/event identifiers, refresh dependencies, redaction, renderer, and executable acceptance cases. Keep proposed, awaiting-input, awaiting-confirmation, executing, succeeded, stale, denied and failed distinct. A streaming progress message must represent a completed or actually running step, not speculation.

There is no uniform generic write protocol: most writes use the `Idempotency-Key` header, folio status takes `idempotencyKey` in the body, and business-day seal rejects any body. Some POSTs are reads. A schema-aware adapter must preserve these differences. Never automatically retry a mutation under a new key after an uncertain response. Read-only preflight is not a reservation lock.

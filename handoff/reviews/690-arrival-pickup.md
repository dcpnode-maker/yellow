## Source findings and corrections

- The travel attempt freezes the current expected arrival tuple, exact proposed tuple and idempotency key before PUT. The linked task attempt freezes task ID, eligible adjacent action and exact status/assignee compare-and-set body before POST. Both are written to session storage before network dispatch; unavailable storage blocks the command. Unknown network/5xx outcomes retain the same request/key and lifecycle lock; exact authoritative readback is required to claim success. A changed readback without exact target no longer discards an uncertain attempt. A definite first rejection clears it and requires a fresh read. The persisted retry parser now validates kind, IDs, action, body keys, tuple types, time and bounded text before allowing a retry.
- My initial review found the task-load effect could invalidate an in-flight parent reservation refresh when that refresh linked a task, leaving reconciliation stranded. The implementer separated component-lifetime and task-read generations, then made the background effect yield to an active command/recheck refresh. A second older-background-read overwrite race was likewise addressed with a task-read token. The mounted exact sequence remains the coordinator's browser acceptance item.
- The parent keys this workspace by property/reservation, joins its lock with other reservation lifecycle locks and refreshes the existing reservation detail. The UI requires human confirmation for travel and each task action, searches existing active staff Party candidates, does not directly change `task` or `travel_detail`, and does not represent pickup as a booked vehicle or charge. The task read checks the exact reservation/task identity; property scope and permission are enforced by existing HTTP routes.
- My final contract spot-check found an unintended UI-only requirement for a schedule before recording pickup intent. The existing arrival travel command permits pickup intent with no schedule, and existing pickup states include “schedule required.” The implementer removed that restriction, added explicit schedule-required versus scheduled-unlinked copy and translated reused departure-time validation wording to arrival-time wording. I personally reran the focused tests after this correction.
- Existing backend HTTP tests demonstrate lifecycle-write property grant for travel and separate dispatch/work property grants for task transitions. The real PostgreSQL suites exercise tenant/property isolation, stale CAS, adjacent task status, actor-bound exact replay, concurrent winners, publication rollback and denied raw runtime DML.

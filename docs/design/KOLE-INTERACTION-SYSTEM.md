## System relationships the design must preserve
Canonical references: docs/YELLOW-CONSTITUTION.md, docs/ARCHITECTURE-V1.md, docs/journeys/MASTER-JOURNEY-MAP.md, docs/design/STAFF-JOURNEYS.md, docs/design/BUILT-CAPABILITY-MANIFEST.md, current frontend ecosystem/capability-registry.ts and commercial-mapping-types.ts. Historical build-status documents are not proof of the current live runtime; use receipts.

- Navigation zoom: portfolio → property → domain → entity → transaction → evidence. Keep property, date, entity and work context in deep links and return paths.
- Guest journey: pre-arrival → arrival → stay → departure → post-departure. Each stage has guest and staff duties, blockers, owners, follow-ups and evidence.
- Reservation/profile: Party identity and visit history are distinct from an individual reservation, occupants/sharers, room segments and folio windows.
- Arrival: reservation → assignment → room condition/inspection → authoritative readiness → confirmed check-in. Cleaning completion or a message does not prove check-in eligibility.
- Departure: reservation → departure services → folio windows and settlement → authoritative checkout. A button or visual status never creates financial truth.
- Room truths: reservation lifecycle, occupancy, housekeeping condition, inventory restriction, guest service state and derived readiness stay distinct.
- Business mix: demand group → market segment; distribution group → source → channel codes; company/agent/account and salesperson relationships are separate dimensions. Do not label Acme Ltd as a distribution source by default.
- Product: room class/category/type and actual sellable/physical units are distinct from business source and demand.
- Commercial decisions: room nights and revenue aggregate by configured dimensions; occupancy/ADR/RevPAR retain denominator, date, currency and lineage. Observed facts, forecasts and recommendations must be visually distinct.
- Work: request → department/owner → acknowledgement → work → evidence → follow-up/escalation. Sent is not completed. Guest and staff views share the record but not all private fields.
- Finance: folio windows → immutable lines → authorized posting/correction/settlement → documents. Exact values and unresolved command outcomes stay visible. Owner trust is not a guest folio.
- AI, voice, UI and integrations all call the same authorized functions. No design action bypasses tenancy, permissions, current-state validation or audit.

## Shared workspace grammar
Stable shell: property context + one universal search + role-shaped navigation. Then concise title/context, reusable compact ribbon, concise view tools, data/work region and conditional inspector. Selection changes within the surface; no unrelated redesign or page reload for sibling views. Standard density tokens, sane row heights, quiet neutral surfaces, consistent outline icons, restrained semantic colors. AI mode can alter ambience without washing out data/status contrast.

Tables: working column menus, active indicators, per-column clear, user-added conditions and unique sort priorities with reordering/removal. Filter controls match actual supported data types. Show loaded-result limits. Mobile supports the same options in a full-height sheet, not a tiny desktop popover.

Search: identify entity + module + relevant stay/room/date in compact rows; reveal secondary actions on selection. All modules discoverable through capability-aware navigation; do not claim all data is indexed before implemented. Read permissions remain authoritative.

## Reservation-table correction — founder feedback, 24 September 2026

The founder explicitly requires room type, room class, rate code and meal plan in booking tables. This is an operational information requirement, not optional visual decoration. Preserve Yellow terminology: room type = Deluxe/Suite/etc.; room class = King/Twin/Queen/etc. Keep assigned room, booked product and charged product distinct. Do not infer class from a display-name substring.

### Primary-source benchmark

- [Oracle: Using the Search Result](https://docs.oracle.com/en/industries/hospitality/opera-cloud/26.1/ocsuh/c_search_result_panel.htm): results support related-record navigation for guest, company/agent/source, reservation, block, balance, room type, rate code and rate information; users can choose/reorder columns with role permission. Yellow should preserve this operational depth within its own visual system.
- [Oracle: Updating Reservations](https://docs.oracle.com/en/industries/hospitality/opera-cloud/25.5/ocsuh/t_managing_reservations_editing_reservation_stay_details.htm): stay details distinguish dates, occupants, room assignment, booked/charged type, rate, market, source and origin; related panels provide packages, shares, alerts, billing and history. This is a reference benchmark, not evidence those capabilities are all live in Yellow.
- [Oracle: About Rate Codes](https://docs.oracle.com/en/industries/hospitality/opera-cloud/26.2/ocsuh/c_rate_codes.htm): rate codes can carry package entitlements. A package can include non-meal services; Yellow must not equate every package with a meal plan.

No Oracle/PMS branding appears in the application. Yellow-specific column, mobile and mapping proposals below are design decisions, not claims that Oracle uses Yellow's terminology.

### Proposed column contract

| Group | Available display/column choices |
|---|---|
| Identity and stay | Guest, booking reference, reservation status, arrival date, departure date, nights, recorded ETA/ETD, adults, children, sharers, booking date |
| Room product | Assigned room, room type, room class; separate booked/charged/assigned product where supported; room condition and assignment status distinct |
| Rate and inclusions | Rate code, rate-plan name, meal-plan code and expanded meaning, packages, date-specific nightly amount and currency; rate breakdown for variable nightly prices |
| Business attribution | MSG, MS, source, channel, company, agent, salesperson, group/block, configured purpose-of-stay classification and evidence |
| Operational/financial context | Authoritative arrival blockers, preferences/alerts, travel/pickup, guarantee/deposit/folio context, exact balance with currency and authorized billing link |

Default arrival view must show room type, room class, rate code and meal plan as separate columns alongside guest/booking/stay/room/status. Optional columns are organized by the groups above, not permanently removed. Support user-selected order, width and pinning, saved lane-specific views, and per-field filter/sort with user-added levels. Arrival and departure remain independent filter/sort fields even when a compact Stay dates cell presents both. Never call transport arrival time the guest's recorded ETA. Missing/unknown is not zero, room-only, or confirmed.

Multi-room or multi-segment bookings expand into their actual room/stay segments; show a clear Multiple indicator instead of presenting the latest segment as the whole booking. Nights follow the agreed property-local stay semantics, not naive elapsed-hours arithmetic. A variable nightly rate opens a dated breakdown; do not silently label an average or total as Nightly. Monetary amounts remain exact minor-unit values with explicit currency.

Mobile shows the four requested fields in an expanded booking summary and provides all column/rule choices plus full authorized reservation editing in focused sections. A display breakpoint must never be the sole reason a field or operation becomes unreachable. Opening guest/profile/history/folio or an edit form preserves the selected booking and return context.

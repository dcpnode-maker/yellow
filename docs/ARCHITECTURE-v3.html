2. Core Domain Model Decisions (Locked)

2.1 Folio Ownership

Folio is owned by an Account (Guest, Company, House, Outlet, Event, Trust, etc.). A Reservation links to one or more Folios; it does not own them. Billing windows are folios that share an owner.

Why: Required for house accounts, walk-in POS charges, banquet/event billing, deposits taken before a booking exists, and group masters that outlive individual stays. Confirmed by multiple modern systems.

2.2 Composite Inventory

Space (physical) → SellableUnit (configuration of one or more Spaces) → Slot (SellableUnit × time interval). Mutual exclusivity enforced by a space_occupancy projection with partial exclusion constraint.

Why: Correctly handles dorm beds vs private rooms, connecting suites, and keeps the model open for future verticals without core rewrites.

2.3 BillingAutomation

Static routing is generalised into a BillingAutomation (trigger + condition + action). Routing, fixed charges, deposit schedules, conditional transfers and payment plans are instances of one mechanism.

2.4 Insert-only Fact Log

One insert-only temporal pattern serves ledger corrections, rate/reservation corrections, and configuration versioning. “Current” is always derived via query; never stored via UPDATE. Every fact carries both valid-time (when it is true in the business) and recorded-at (when the system learned it), so retroactive corrections and forward-dated changes are the same operation.

2.5 Tenancy

Two tiers only: Shared schema + RLS (default) and Dedicated database (regulatory or contractual isolation). Schema-per-tenant is dropped.

2.6 Fiscal Strategy

Build the tax calculation engine (value-banded, per-night/person/room, capped nights, category-banded, compounding, exemptions). Build fiscal document issuance in-house for the first two jurisdictions — ZATCA (Saudi) and India IRP, both free government APIs — behind the unchanged FiscalDocumentProvider interface supporting the five global mandate patterns. Buy trigger: jurisdiction #3, where a provider’s multi-country maintenance beats ours. Statutory guest registration remains in-house (no provider aggregates it).

2.7 Inventory Authority & Single Choke Point

PostgreSQL is authoritative for every sellability decision. Valkey holds a read projection, invalidated by event, and is never consulted to approve a booking — a stale projection can only show a room that turns out to be gone (recoverable), never create a double-booking. space_occupancy is written only by one SECURITY DEFINER function; direct table access is revoked from the application role, and a CI test asserts that direct writes fail.

Why: Two sources of truth for the one invariant that must never break is a correctness failure waiting for a concurrency edge case — and a bypassed write path would disable double-booking protection while the constraint still looked healthy.

2.8 Inventory System of Record (per property)

inventory_authority is a per-property, per-channel setting: PMS-authoritative (reservation ingestion does not alter upstream availability; the PMS pushes counts) or CRS-authoritative (the CRS derives availability; PMS pushes are suppressed and allocation is consumed). Both modes still write space_occupancy locally — physical integrity is never delegated, only commercial availability.

3. Key Bounded Contexts & Capabilities

Reservation & Groups

Full lifecycle, multi-room, multi-segment, shares, linked parties. Unified ReservationGroup (kind = linked | block | share) replaces separate master/block/share hierarchies.

Inventory & Availability

Composite slots, Postgres-authoritative writes with Valkey read projection, space_occupancy exclusion constraint, overbooking limits per service/date range, restrictions, holds, real-time ARI push.

Profile / CRM

Guest, Company, Agent, Source, Group, Vendor, Contact. Owner and Agent are first-class party types. Relationships, preferences, memberships, consent, stay history, duplicate detection & merge.

Financials (Native Hotel Finance)

Account-owned folios, posting engine, immutable postings, BillingAutomations, payments (tokenised), deposits, AR, cashier sessions, continuous day-close, trial balance, owner statements. Strong native module so most hotels do not need a second finance system. Clean export/sync to QuickBooks, Xero, SAP, etc.

Rooms & Housekeeping

Condition + occupancy axes, task sheets with credit weighting, mobile attendant, discrepancies, work orders, queue management.

Groups, Events & Banquets

Blocks, wash schedules, rooming lists, function space, BEOs, event billing to master folio.

Statutory Registration

Distinct concern supporting country-specific formats, deadlines and transports (Italy Alloggiati 168-char, Portugal SIBA, India Form C, Croatia eVisitor, etc.).

Tax & Compliance

Rules-driven tax calculation engine. Fiscal documents via provider interface. USALI 12th Edition as baseline revenue classification and statistical schema.

Distribution

Direct Booking.com + Expedia adapters primary (free connectivity partner APIs; certification is calendar, not cash). RateGain UNO / SiteMinder plug-compatible behind the same interface for long-tail expansion. GDS connectors, direct booking engine, aggregation layer for channel granularity differences.

Ancillary Operations

Native support for charging, tasking and guest billing for Spa/Salon, Retail outlets, Concierge, Bell Desk, Valet/Parking. Deep specialised scheduling may start as integration; money and guest record stay in the PMS.

4. Vertical Scope & Profiles

v1 commercial scope: Hotels, Hostels, Serviced Apartments, Short-Term Rentals.

Inventory units carry typed attributes and constraint predicates via Vertical Profiles. The architecture remains open so Marina, Campground or RV support can be added later as profiles without core rewrites. Full marina/campground geometry and vessel matching are explicitly deferred.

5. Trust Accounting

Not a new subsystem. Composed from existing primitives: Account with role = trust, BillingAutomation rule for owner/fee split, reconciliation report, and payout integration.

7. Design Principles (Standing)

  • Reuse — prefer instances of existing primitives over new mechanisms.
  • Data, not code — behaviour expressed as schema-validated configuration wherever possible.
  • Single choke point — every path that must preserve an invariant flows through one place.
  • Insert-only temporal model — one pattern for ledger, rates, reservations and configuration versioning.
  • Extension Registry — one lifecycle mechanism for vertical profiles, tax jurisdictions, statutory adapters, fiscal providers and future plugins. Content stays typed per type.
  • One precious datastore — PostgreSQL is the only stateful system whose loss matters; Valkey, NATS, search indexes and dashboards are derived and disposable, rebuilt from Postgres by script.
  • Seven surfaces, one codebase — every client surface is a mode (route + role Grant + display mode) of a single PWA, not a separate product.
  • Model gateway — AI features run local-first (Whisper.cpp, Piper, pgvector, quantised open-weight LLM) with Claude as a per-tenant paid tier behind the same interface; customer revenue funds frontier quality.
  • Maintenance is automated, or it doesn’t ship — pinned compose file, Renovate PRs, daily contract tests, dashboards-as-code, weekly restore-proof. Founder budget: 2–4 hours/month.
  • Lowest cost to build, run and maintain — buy what changes frequently (fiscal documents — from jurisdiction #3), build what is core and slow-changing (tax calculation, hotel finance, inventory integrity).
  • Rank #1 experience — staff feel proud and fast; guests feel delighted.

11. Seven Surfaces, One Codebase

Web App

The PWA itself — front desk, manager, admin. Keyboard-first, dense grids, command palette; Rank-1 UX targets unchanged.

Staff Mobile

Same PWA installed via manifest; housekeeping and task views are routes gated by role Grant.

Guest Mobile

Same PWA, guest Grant scope: booking, folio, requests, messages, digital key when the lock vendor lands.

Front-Desk Desktop

PWA, or a Tauri (MIT) wrapper where native key-encoder/peripheral access is required — a build target, not a second app.

Kiosk

Chromium kiosk mode on any tablet the hotel buys (their capex); kiosk Grant scope shows the check-in flow only.

Partner Portal

A route + partner Grant scope over the same public API. No separate product.

Voice

Web audio → Whisper.cpp → intent → the same command-palette actions → Piper reply. A thin input method over an API-first system.

What was priced as months of build across five extra surfaces collapses to routes, role grants and two wrappers — because API-first means every surface is a client of the same contract. The scope returns; the cost does not.

13. Reliability, Maintenance & Spend Triggers

  • One compose file defines the entire stack — reproducible anywhere in minutes, which is itself the DR plan.
  • Renovate opens version-bump PRs; daily CI contract tests against OTA and fiscal sandboxes gate every merge.
  • pgBackRest continuous archiving offsite; weekly scripted restore proves the backup is real.
  • Streaming replica + one-command promote runbook — deliberate manual promotion; no split-brain machinery. RTO 2–5 minutes.
  • Unattended security upgrades; Uptime Kuma + healthchecks.io alert both phones.
  • Everything non-Postgres is disposable — kill-and-rebuild scripts exist and are drilled monthly.
  • Founder time budget: 2–4 hours/month. A component that breaks the budget is replaced or removed — price is not a defence.

Spend-Money Triggers (each observable, none speculative)

  • ₹4k Hetzner box — when free-tier comfort runs out after first revenue.
  • Managed Postgres — when founder ops time on the database exceeds budget two months running.
  • Fiscal provider — jurisdiction #3.
  • Channel manager plug-in — long-tail OTA expansion beyond the direct 2–3.
  • Claude tenant tier — funded by the AI premium price, never by us.
  • ClickHouse cluster — when a DuckDB report crosses seconds.
  • Second app instance / automated failover — first enterprise SLA contract.

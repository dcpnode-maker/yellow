# First GPU coding-model smoke — 28 September 2026

The private synthetic Kaggle GPU notebook ran official
`Qwen/Qwen2.5-Coder-1.5B-Instruct` at fixed revision
`2e1fd397ee46e1388853d2af2c993145b0f1098a`. The first attempt loaded
weights but failed because tokenization output was passed as one positional
argument to `generate`. The local cell was repaired to call
`generate(**tokens, ...)`; local contract tests passed before the retry.

The retry took **3.74 s to load** and **10.69 s to generate** a response, with
**6,203,848,704 bytes** peak memory allocated on GPU 0. This is a one-prompt
smoke, not a representative throughput benchmark.

The generated `collapse_ranges` code **failed the requested contract**:

- It sorted `intervals` in place, mutating the caller's input.
- It did not reject a range whose end precedes its start.
- Its second asserted result merged `(1, 6)` and `(8, 9)`, which are not
  touching closed integer ranges.
- The response continued after the code block and was cut at the 240-token cap.

The output was not executed or applied to Yellow. This result rules out
selecting the 1.5B model as a Yellow coding worker on current evidence. It
does not prove that larger models will pass. The GPU session's shutdown could
not be verified after the original browser tab switched accounts, so Order
683's shutdown acceptance remains open.

## Worker 2 bounded Qwen3.8 coding result (Order 684)

The first `llama-cli` invocation reached the model but waited in interactive
mode and hit the 600-second process limit; it was not a model-speed result.
The repaired local probe set `--single-turn` and detached stdin. Its default
thinking run exited successfully in 76.16 s but exhausted the 384-token cap
in analysis and emitted incomplete Python. This configuration failed the
requested code rubric.

The second invocation used the pinned Q4_K_M GGUF and source-built llama.cpp
with `--reasoning off`, `--split-mode layer`, `--tensor-split 1,1`,
`--n-gpu-layers 999`, 2,048-token context, 384-token output cap and seed 1.
The notebook returned exit code 0 in **23.09 s**. Peak GPU memory was
**7,333 MiB / 8,425 MiB** (before/after 105 MiB on each); reported prompt and
generation rates were **144.3 and 13.3 tokens/s**. The CLI did not report exact
token counts or a separate model-load duration in this output, so neither is
claimed. This is one warm-source-build, single-turn observation, not a service
throughput or Yellow-task benchmark.

The complete generated `coalesce_nights` function is transcribed only in
`qwen38_sample_output.py` for the model rubric. Four local test cases cover
empty/disjoint input, overlap/adjacency, no input mutation and reversed-date
rejection; all four cases pass. The output was never executed in the Kaggle notebook or applied
to Yellow. One successful synthetic function is insufficient to call this a
dependable autonomous coding worker; next evaluation needs multi-file tasks,
patch application under review, and repeatability.

This was the official Qwen3.8-27B base-model family through an Unsloth GGUF
quantization, **not** an evaluated community “uncensored” derivative. Any
derivative requires its own provenance and same-rubric test.
